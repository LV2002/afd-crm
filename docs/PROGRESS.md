## Session 1 — Phase 0 scaffold + auth + dynamic permissions + RLS — 2026-08-27

**Shipped:**
- Next.js 15.5.24 (App Router, TS strict, Tailwind v4), pinned to match CLAUDE.md's stack
  table rather than `create-next-app@latest`'s Next 16.
- shadcn/ui components (`button`, `input`, `label`, `card`, `badge`, `separator`, `avatar`)
  hand-built from Radix primitives — `ui.shadcn.com` is blocked by this environment's
  network policy, so `shadcn init`/`add` don't work here. Same output, no CLI dependency.
- Three Supabase client modules: `src/lib/supabase/{browser,server,service-role}.ts`.
  `service-role.ts` and `server.ts` both import `server-only`, so an accidental import from
  a client component is a build error, not a runtime leak.
- `src/lib/auth/permissions.ts` — the 34-permission-primitive constant, the single source of
  truth `permissions` is seeded from.
- Drizzle schema (`src/lib/db/schema/*.ts`) for every Phase 0 table: `org_settings`,
  `terminology`, `centers`, `profiles`, `user_centers`, `permissions`, `roles`,
  `role_permissions`, `dropdown_categories`, `dropdown_options`, `pipeline_stages`,
  `field_definitions`, `audit_log`. `profiles.id` has a real FK to `auth.users.id` (declared
  via a reference-only `pgSchema("auth")` table Drizzle never migrates).
- Two migrations in `src/lib/db/migrations/`:
  - `0000_whole_purple_man.sql` — generated by drizzle-kit, hand-edited to remove the
    `CREATE SCHEMA "auth"` / `CREATE TABLE "auth"."users"` statements it generates by
    default (that table is Supabase's, not ours — see comment at the top of the file).
  - `0001_functions_and_rls.sql` — hand-written: `auth_center_ids()`, `auth_scope(perm)`,
    `can_access_center(perm, center_id, owner_id)`; `updated_at` triggers; the two
    lockout-protection invariants as constraint triggers (settings-admin-of-last-resort, and
    the protected `admin` role); a trigger blocking deletion of `is_core` field
    definitions; a defence-in-depth trigger blocking self role/is_active changes; and RLS
    policies (enabled + policy per table) on all 13 tables, every one branching on
    `auth_scope()`/`can_access_center()`, never on a role name or code.
- **RLS and the lockout triggers were verified against a real local Postgres 16 instance**
  (not just read for correctness) — a throwaway shim reproduced `auth.uid()` and the
  `authenticated`/`anon`/`service_role` roles, both migrations were applied, the seed was
  run, and then, as five simulated users spanning admin/center_head/counsellor:
  counsellor sees only their own profile row; center_head sees only profiles sharing their
  centre; admin sees everyone; only `settings.manage='all'` can write `org_settings`, and a
  second row is rejected by a unique index even for admin; deactivating the last
  `settings.manage='all'` admin is blocked; deleting/stripping/un-protecting the `admin` role
  is blocked; a center_head cannot self-promote to admin; a core field definition cannot be
  deleted; `audit_log` accepts inserts from anyone but only `audit.read` holders can select,
  and update/delete are rejected for everyone including admin (no policy exists for either).
  The database was dropped after.
- Seed script (`npm run db:seed`, idempotent): 2 centres, 34 permissions, 6 roles with
  bundled `role_permissions` (see `docs/DECISIONS.md` for the bundle each role got), 10
  dropdown categories / 60 options, 14 pipeline stages, 29 core `field_definitions` for
  `entity='lead'`, and 6 Supabase Auth users (one per role) via the service-role admin API —
  only runs the user step when `SUPABASE_SERVICE_ROLE_KEY` is set, so the rest of the seed
  still works against a project with auth not yet configured.
- Auth: email/password login via Supabase Auth (`(auth)/login`, a Server Action, React 19
  `useActionState` for the error state), middleware-based session refresh + redirect
  (`src/middleware.ts`), sign-out as a Server Action.
- `getCurrentUser()` (`src/lib/auth/session.ts`) resolves profile + role + the caller's full
  permission→scope map through the RLS-bound server client — it cannot see more than the
  user's own session is allowed to.
- Permission-gated app shell (`(app)/layout.tsx`): sidebar built from `navItemsFor(user)`
  (`src/lib/auth/nav.ts`), which filters a static nav list by `can(user, permission)` — no
  nav item has a role name anywhere near it. Stub pages for dashboard/my-day/leads/pipeline/
  reports/ask/settings each re-check their own required permission server-side and render
  `<AccessDenied/>` if missing, so a direct URL hit is also gated, not just the sidebar link.
- `npx tsc --noEmit`, `npx eslint .` and `npm run build` all pass clean.

**Stubbed:** every page under `(app)/` beyond dashboard is a placeholder naming the phase
that actually builds it. No settings screens yet (Session 2). No `leads`/`students`/etc.
tables yet (Phase 1) — `field_definitions` seed data for them exists ahead of the tables.

**Known broken:** nothing. `tests/rls.spec.ts` (an automated version of the manual RLS
verification above) is Session 3's job per `docs/02-BUILD-PHASES.md`, not this one's.
